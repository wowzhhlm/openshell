# openshell · 网络拓扑引擎评估与升级方案

> 版本：v1.0 ｜ 日期：2026-11-21 ｜ 项目：`D:\openshell`
> 对应需求：「现在的网络拓扑配置工具不是太智能，有无其他 star 更多的开源项目可以使用。」

---

## 1. 问题与评估目标

当前拓扑配置工具集成的是 `bobhe2016/net-topo-cmd-generator-web`（纯前端、AntV G6、中文、多品牌 CLI 模板）。用户反馈两点：

1. 功能「不够智能」——缺少自动规划、冲突检测、配置校验、命令解释、批量导出；
2. 希望换成 **star 更多的开源项目**。

本报告的结论基于 GitHub 仓库现状（star 数为调研时近似值，会随时间变化，请以仓库页面为准），按以下硬约束筛选替代品：

| 约束 | 说明 |
| --- | --- |
| A. 纯前端 / 可内嵌 Electron | 无 Python/Java 后端、无数据库、无需常驻服务 |
| B. 中文界面与中文命令解释 | 面向国内网络工程师 |
| C. 拓扑图 → 多厂商 CLI 自动生成 | 至少华为 VRP、思科 IOS、H3C Comware |
| D. 离线可用 | 无 CDN、无外部 API |
| E. 许可证清晰可分发 | 有 LICENSE 文件，且许可允许打包进桌面应用 |

### 关键结论

> **不存在一个「star 更多」且同时满足 A–E 全部约束的现成项目。**

- star 更高的项目（NetBox、Batfish、netmiko、containerlab、GNS3、drawio）都是**不同赛道**：IPAM/DCIM、配置验证、自动化下发、网络仿真、纯绘图，且绝大多数需要后端服务或 Python/Java 运行时，无法塞进 Electron 的纯前端窗口。
- star 更低或相近的项目（nwiz、NetSim Studio 镜像）在许可证（GPL-3.0 / 无许可证 / 作者失联）或技术形态（Tauri、需 Express）上比现用引擎更差。
- 唯一在功能上完全贴合的仍是现用引擎；它的问题是「不够智能」和「许可证不完整」，而不是「star 少」。

单纯换项目**不能**解决「不够智能」，反而会引入 GPL 传染、后端依赖、英文界面与许可证缺失等新风险。因此推荐路线是：**保留引擎 + 净化合规 + 自研智能层**。

## 3. 现用引擎的三个实际风险（已核查源码）

| # | 风险 | 证据 | 处置 |
| --- | --- | --- | --- |
| 1 | 许可证不完整 | GitHub API `license: null`，仓库根目录无 `LICENSE`；仅 README 口头写 MIT | 详见 `src/topology/THIRD_PARTY_NOTICES.md`；记录来源、标注「待作者补充书面授权」，并规划 Phase 2 自研模板替换 |
| 2 | 混淆 boot loader 不可审计 | `app.js` 第 37 行内嵌 `atob` + XOR（`NetTopo2026`）的 66752 字符单行代码 | **已移除**。静态解码确认它只是把一张第三方「赞赏二维码」JPEG 注入 DOM，并非远程加载器，但混淆代码违反本项目「可审计 / 严格 CSP」承诺 |
| 3 | 第三方变现内容随产品分发 | 左侧「支持工具」打赏区块、关于弹窗收款码、悬停放大弹层 | **已移除**，替换为中性的「关于本工具」说明（引擎来源、智能化增强、许可证状态） |

> 说明：上述清理只删除「不可审计代码 + 原作者收款码」，不改动拓扑绘图与 CLI 模板逻辑，属于集成侧净化，不改变功能。

## 4. 推荐方案：三层结构

```
┌─────────────────────────────────────────────┐
│ 第 3 层  智能增强（本次自研，MIT，可审计）        │
│  smart-config.js 纯函数引擎                    │
│  smart-panel.js  UI 接入层                    │
│  · 自动 IP / VLAN 网段规划                     │
│  · IP / VLAN 冲突检测                          │
│  · 配置体检（评分 + 修复建议）                  │
│  · 命令逐行中文解释                            │
│  · 批量导出为每台设备独立 .cfg 脚本包           │
├─────────────────────────────────────────────┤
│ 第 2 层  拓扑绘图 + CLI 模板（现用开源引擎）     │
│  G6 画布 / analyzer.js / templates/*           │
│  仅作为「被调用的能力」，不复制其实现            │
├─────────────────────────────────────────────┤
│ 第 1 层  Electron 宿主                        │
│  独立窗口 + 有限 preload + 文件写入 IPC         │
│  导出结果统一落盘 D:\openshell\导出     │
└─────────────────────────────────────────────┘
```

**合规要点**：第 3 层全部自研，不复制第 2 层代码；第 2 层的许可证缺口单独文档化并给出替换路线。这样即使未来需要整体替换第 2 层，智能层也能无缝保留。

## 5. 本次已落地的智能化能力

| 能力 | API | 说明 |
| --- | --- | --- |
| 拓扑数据采集 | `SmartConfig.fromGraph(graph)` / `normalize(topology)` | 复用 `analyzeTopology()`，输出规范化 `{devices, edges, allTopologyVlans}` |
| IPv4 工具集 | `isValidIpv4 / ipToInt / intToIp / networkOf / broadcastOf / sameSubnet / maskToPrefix / prefixToMask` | 纯函数，零依赖 |
| 自动 IP 规划 | `planIP(topology, opts)` | 按 VLAN 分配 `10.<site>.<vlan>.0/24`，网关 `.1`、设备从 `.10` 起；跳过已填 IP、自动避让冲突；返回 `assignments` 可直接回填画布 |
| IP 冲突检测 | `detectIPConflicts(topology)` | 重复 IP、非法格式/掩码、网关跨网段、网络号/广播地址误用 |
| VLAN 冲突检测 | `detectVlanConflicts(topology)` | ID 越界、设备内重复 ID、同 VLAN 跨设备网段不一致、Trunk 两端 VLAN 不一致提示 |
| 配置体检 | `validateConfig(topology)` | 汇总 error/warn/info，给出评分与逐条修复建议；含孤立设备、未选厂商、三层设备缺管理 IP 等结构检查 |
| 一键应用规划 | `autoApplyPlan(topology, plan)` | 生成 `{deviceId: {field: value}}` 补丁，UI 可写回 `graph.updateItem` |
| 命令中文解释 | `explainLines(text, vendor)` / `explainCommands(text, vendor)` | 内置华为/思科/H3C/锐捷通用命令规则库，输出「命令 → 中文说明」对照 |
| 批量导出 | `splitDeviceScripts(text)` / `buildPackage(files, meta)` / `batchExport(...)` | 把 `CmdTpl.generateAll()` 的合并输出拆成每台设备独立 `.cfg` 文件 + 清单 + 合并包 |
| 报告渲染 | `formatReport(report)` | 插入终端输出顶部的体检摘要 |

### UI 接入点

- 工具栏新增两个入口（由 `smart-panel.js` 动态注入，不改第三方源码）：「🧠 智能体检」打开分析面板、「🗂 批量导出」直接跳到导出工作区。
- 新增「智能分析面板」，内含四个工作区：🩺 体检报告 / 🌐 IP 与 VLAN 规划 / 📖 命令逐行解释 / 🗂 批量导出。
- 批量生成命令时「后置增强」：在原有终端弹窗顶部插入体检摘要，可开关「命令解释」。
- 拓扑窗口新增最小权限 preload：`topoApi.saveConfigPackage()` 经主进程校验后写入 `D:\openshell\导出\`，符合「生成结果统一保存到 D 盘」约定。

## 7. 后续可选升级路线（非本次范围）

| 阶段 | 目标 | 候选 |
| --- | --- | --- |
| Phase 2 | 消除许可证缺口：用 YAML 模板自研 CLI 生成引擎，替换 `templates/*` | 借鉴 `giaccount/switch-config-generator`（MIT）的模板组织方式，仅借鉴思路 |
| Phase 3 | 配置下发前的形式化校验（ACL 冲突、路由环路、未定义 VLAN 引用） | 借鉴 Batfish 的验证思路，落地为纯前端规则 |
| Phase 4 | 可选服务端：资产台账 / IPAM / 多用户协作 | NetBox（Apache-2.0）作为独立服务，通过 REST 对接，不内嵌 |
| Phase 5 | 批量下发与回滚 | netmiko / NAPALM / Nornir 作为独立 Python 服务，经现有 SSH 通道调度 |

> 这四期都保持「智能层自研、宿主层 Electron、外部组件可选」的边界，避免在桌面应用里引入 GPL 或重后端依赖。

## 8. 一句话回答用户

**没有「star 更多又能直接用」的替代品**：star 更高的都是需要后端或不同赛道的工具，star 相近的许可证更差。本次不换引擎，改为**清除混淆代码与第三方收款码、补齐合规说明、自研智能增强层**，把「不够智能」的问题实质解决掉；同时给出 Phase 2 的自研模板替换路线，彻底消除许可证风险。
